# Day47 — Cartographer 파라미터와 2D SLAM 튜닝

> 원본: [cartographer parameter](https://app.notion.com/p/3f979696939580eaa6e4ed81583266d4) · 노션 작성일: 2026-10-14 · 정리일: 2026-10-15  
> 강의 메모에 개념 설명, 실습 점검 순서, 공식 자료로 확인한 정정 내용을 추가했다. 아래 예시는 사용 중인 ROS 2 배포판과 Cartographer 포크의 실제 설정 파일에 맞춰 적용한다.

## 1. 오늘의 핵심

Cartographer 튜닝의 목표는 **벽이 잘 맞는 지도와 실시간으로 갱신되는 위치 추정**을 함께 얻는 것이다. 숫자를 무조건 작게 하거나 점수를 높이는 것으로 해결되지 않는다.

- 먼저 센서 데이터와 좌표계가 올바른지 확인한다.
- 원거리 노이즈, 포인트 수, 지도 해상도 사이의 균형을 맞춘다.
- 같은 주행 데이터에서 설정을 하나씩 바꿔 비교한다.
- 지도 품질뿐 아니라 CPU 사용량과 처리 지연도 함께 기록한다.

## 2. Gazebo와 Cartographer의 역할

| 도구 | 역할 | 강의에서 다룬 조정 대상 |
| --- | --- | --- |
| Gazebo | 로봇과 환경, 센서 측정을 시뮬레이션 | 센서 노이즈, 조명, 벽의 재질, 물리적 환경 |
| Cartographer | 입력 센서를 이용해 위치와 지도를 추정 | 거리 제한, 필터, 스캔 정합, 서브맵, 최적화 |

Gazebo에서는 같은 환경을 반복해서 실험할 수 있다. 예를 들어 장애물 배치를 고정한 뒤 센서 노이즈만 바꾸면, SLAM이 측정 오차에 얼마나 민감한지 비교하기 쉽다. 센서 종류와 설정 예시는 [Gazebo 센서 문서](https://gazebosim.org/docs/latest/sensors/)를 참고한다.

**메모 보완:** “현실과 거의 동일”은 실습의 목표로 이해해야 한다. 화면상 아크릴이 투명하거나 반사한다고 해서 실제 라이다의 투과·다중 반사·미검출까지 자동 재현되는 것은 아니다. 사용한 센서 모델과 렌더링 방식의 지원 범위를 확인해야 한다. “Cartographer에서 직접 하는 것보다 빠르다” 역시 환경 실험의 편의성에 관한 메모로 보고, 계산 속도 비교로 일반화하지 않는다.

## 3. 2D SLAM 처리 흐름

```text
라이다 측정 → 거리 제한·다운샘플링 → 위치 예측·스캔 정합
                                      ↓
                                 Motion filter
                                      ↓
                              서브맵에 측정 반영
                                      ↓
                       루프 폐쇄 제약 탐색·전체 위치 최적화
```

Local SLAM은 가까운 구간에서 일관된 서브맵을 만들고, Global SLAM은 서브맵과 궤적 사이의 관계를 조정한다. 이미 만들어진 서브맵 내부의 찌그러짐을 전역 최적화만으로 완전히 복원할 수 있다고 기대해서는 안 된다. [알고리즘 설명](https://google-cartographer-ros.readthedocs.io/en/latest/algo_walkthrough.html)

2D 설정은 주로 평면 이동을 전제로 한다. 경사로, 큰 기울어짐, 서로 다른 높이에서 측정한 벽은 평면 가정에 맞지 않는 데이터를 만들 수 있다.

## 4. 라이다 거리 제한과 두 개의 라이다

`TRAJECTORY_BUILDER_2D.min_range`와 `max_range`는 사용할 거리 범위를 미터 단위로 지정한다. 멀리 있는 불안정한 측정을 제외하면 도움이 될 수 있지만, 너무 짧게 자르면 위치를 구분하는 벽과 모서리도 잃을 수 있다. [알고리즘 설명](https://google-cartographer-ros.readthedocs.io/en/latest/algo_walkthrough.html)

**메모 보완:** 라이다가 두 개라는 이유만으로 `max_range`를 반드시 줄이는 것은 아니다. 두 센서의 데이터가 늘어 계산량이나 노이즈가 문제가 될 때 검토할 선택지다.

실습에서는 다음 순서로 살펴본다.

1. 각 센서의 스캔이 따로 보았을 때 정상인지 확인한다.
2. 로봇이 정지했을 때 두 센서가 같은 벽을 같은 위치에 표시하는지 확인한다.
3. 센서의 장착 위치·방향을 표현한 TF와 타임스탬프를 확인한다.
4. 주행 중에만 어긋난다면 시간 정렬과 움직임에 따른 왜곡을 의심한다.
5. 그다음 거리 제한이나 다운샘플링을 조정한다.

정지 상태에서도 두 벽이 평행하게 갈라진다면 범위 제한보다 센서 간 좌표 변환부터 점검하는 편이 합리적이다.

## 5. Voxel filter와 지도 해상도

두 값은 모두 공간 크기와 관련되지만 목적이 다르다.

| 항목 | 의미 | 값을 작게 했을 때 |
| --- | --- | --- |
| `voxel_filter_size` | 포인트를 줄이는 공간 구획 크기 | 더 많은 세부 형상 유지, 계산량 증가 가능 |
| `submaps.grid_options_2d.resolution` | 서브맵 격자 한 칸의 실제 길이 | 더 촘촘한 지도, 메모리·계산 부담 증가 가능 |

단위는 미터다. `resolution = 0.05`이면 한 칸이 5 cm다. 같은 10 m × 10 m 영역을 나타낸다고 가정하면:

- 0.05 m 격자: 200 × 200 = 40,000칸
- 0.025 m 격자: 400 × 400 = 160,000칸

격자 한 변을 절반으로 줄이면 같은 면적의 칸 수는 네 배가 된다. 이것이 센서가 측정한 원본 포인트 수까지 네 배가 된다는 뜻은 아니다. Voxel filter와 지도 격자는 구분해서 이해한다. [알고리즘 설명](https://google-cartographer-ros.readthedocs.io/en/latest/algo_walkthrough.html)

## 6. Scan matching, 두꺼운 벽, 드리프트

Scan matching은 현재 측정한 벽과 모서리를 기존 서브맵에 맞추어 로봇 자세를 추정하는 과정이다. 같은 벽이 여러 위치에 반복해서 기록되면 지도에서 두껍거나 여러 겹으로 보인다.

드리프트는 이동하면서 추정 오차가 누적되는 현상이다. 다만 두꺼운 벽만 보고 드리프트라고 단정할 수는 없다.

| 관찰 | 우선 점검할 후보 |
| --- | --- |
| 정지 상태에서도 벽이 흔들림 | 센서 노이즈, TF, 주변 물체 움직임 |
| 회전할 때 벽이 크게 벌어짐 | 타임스탬프, 센서 장착 변환, 회전 추정 |
| 긴 복도에서 진행 방향으로 미끄러짐 | 반복적인 구조, 특징 부족, 위치 예측 오차 |
| 출발점으로 돌아왔는데 지도가 어긋남 | 누적 오차, 루프 폐쇄 성립 여부 |
| 시간이 지날수록 화면이 늦어짐 | 처리 대기열, CPU 부하, 입력 빈도 |

이 표는 원인 확정표가 아니라 실습 진단 순서다. 같은 경로를 낮은 속도로 다시 주행해 증상이 줄어드는지도 비교하면 좋다.

### Score 해석

정합 점수는 후보가 지도에 얼마나 잘 맞는지 판단하는 지표이며, 위치가 맞을 확률 그 자체는 아니다. 반복 구조에서는 잘못된 장소도 높은 점수를 받을 수 있다.

`POSE_GRAPH.constraint_builder.min_score`를 높이면 제약을 더 엄격하게 받아들인다. 너무 높이면 유효한 루프 폐쇄도 놓칠 수 있다. 따라서 “점수가 높을수록 좋다”와 “임계값을 계속 높이면 좋다”를 구분한다. [알고리즘 설명](https://google-cartographer-ros.readthedocs.io/en/latest/algo_walkthrough.html)

## 7. Ceres 값은 언제 바꾸는가?

강의의 “일단 변경하지 않기”는 좋은 출발점이다. 다만 기본값이 모든 로봇에 대한 최적값이라는 뜻은 아니다. 공식 튜닝 문서도 센서와 환경에 따라 가중치를 조정하는 사례를 제공한다.

- `occupied_space_weight`: 측정과 지도 일치를 강조한다.
- `translation_weight`: 예측 위치로부터의 이동 편차를 억제한다.
- `rotation_weight`: 예측 방향으로부터의 회전 편차를 억제한다.

위치·회전 가중치를 높여도 예측 자체가 잘못되면 결과가 나빠질 수 있다. 먼저 센서·TF·시간 문제를 해결하고, 기준 설정을 저장한 뒤 한 항목씩 바꾼다. 한 구간만 좋아지는지, 다른 구간에서도 유지되는지 함께 검증한다. [공식 튜닝 방법](https://google-cartographer-ros.readthedocs.io/en/latest/tuning.html)

## 8. Motion filter와 각도 단위

Motion filter는 비슷한 자세에서 얻은 데이터를 계속 삽입하지 않도록 걸러낸다. 이전에 채택한 데이터와 비교해 시간·이동 거리·회전 변화가 **모두** 임계값 이내이면 삽입을 생략한다. 첫 데이터는 이 비교로 버리지 않는다. [구현 코드](https://github.com/cartographer-project/cartographer/blob/master/cartographer/mapping/internal/motion_filter.cc)

| 파라미터 | 단위 |
| --- | --- |
| `motion_filter.max_time_seconds` | 초 |
| `motion_filter.max_distance_meters` | 미터 |
| `motion_filter.max_angle_radians` | 라디안 |

메모의 `max_angel`은 `max_angle_radians`로 정정한다. `0.1°`와 `0.1 rad`는 다르다.

```lua
-- 0.1도를 지정하려는 경우의 예시. 모든 환경에 대한 권장값은 아니다.
TRAJECTORY_BUILDER_2D.motion_filter.max_angle_radians = math.rad(0.1)
```

- 0.1° ≈ 0.001745 rad
- 0.1 rad ≈ 5.73°

확인한 upstream 기본 설정은 `math.rad(1.)`, 즉 1°다. 수업의 0.1°는 별도 실습 설정일 수 있으므로 실제 Lua 파일과 비교한다. [기본 설정](https://github.com/cartographer-project/cartographer/blob/master/configuration_files/trajectory_builder_2d.lua)

### PID·오도메트리와의 관계

PID 제어는 목표 바퀴 속도 등을 따라가도록 제어 오차를 줄이는 역할이다. 오도메트리는 엔코더 등의 측정으로 이동량을 추정한다. 둘은 연결되지만 같은 기능은 아니다. PID를 잘 조정해도 바퀴 미끄러짐이나 바퀴 반경 오차가 자동으로 사라지지는 않는다.

Motion filter 역시 오도메트리를 교정하는 기능이 아니다. **제어 품질 개선, 이동량 추정 개선, 중복 삽입 억제**를 별개의 문제로 나눠 생각한다.

## 9. Submap 크기와 기본값 90

```lua
TRAJECTORY_BUILDER_2D.submaps.num_range_data = 90
```

확인한 upstream 기본 설정에 90이 들어 있다. 이것은 90 m나 격자 90칸을 뜻하지 않는다. 서브맵을 만들 때 사용하는 range data 삽입 횟수와 관련된 값이다. [기본 설정](https://github.com/cartographer-project/cartographer/blob/master/configuration_files/trajectory_builder_2d.lua)

2D 구현에서는 새 서브맵이 `N`회 삽입을 받으면 다음 서브맵을 생성하고, 앞선 서브맵은 `2N`회 삽입을 받으면 완료한다. 두 서브맵에 겹치는 구간이 생기는 구조다. 따라서 N=90을 “서브맵마다 원본 라이다 메시지 정확히 90개”라고 해석하면 부정확하다. 누적과 필터를 거친 삽입 데이터 기준이며, 일반적인 완료 시점은 180회다. [서브맵 구현](https://github.com/cartographer-project/cartographer/blob/master/cartographer/mapping/2d/submap_2d.cc)

너무 큰 서브맵은 내부에 오차가 누적될 여지가 있고, 너무 작으면 장소를 구분할 구조가 부족할 수 있다. 크기는 주행 속도와 데이터 채택 빈도의 영향도 받는다. [공식 튜닝 방법](https://google-cartographer-ros.readthedocs.io/en/latest/tuning.html)

## 10. CPU와 지연을 함께 확인하기

CPU 점검 창은 계산 부담을 확인하는 데 유용하다. 다만 CPU 사용률만으로 센서 입력부터 위치 출력까지의 지연을 직접 알 수는 없다. 지도 갱신, 메시지 시간, 처리 관련 로그를 함께 비교한다.

실습 기록 예시:

| 실험 | 변경 | 벽 겹침 | 복귀 지점 오차 | CPU·지연 관찰 |
| --- | --- | --- | --- | --- |
| 기준 | 기존 설정 | 기록 | 기록 | 기록 |
| A | Voxel 크기만 변경 | 기록 | 기록 | 기록 |
| B | 거리 제한만 변경 | 기록 | 기록 | 기록 |

입력 빈도와 데이터량을 줄이면 계산이 가벼워질 수 있지만 지도 정보도 줄어든다. 공식 가이드는 품질을 확보한 뒤 실시간 처리가 유지되도록 조정하고, 한 번에 한 항목씩 시험하도록 권한다. [공식 튜닝 방법](https://google-cartographer-ros.readthedocs.io/en/latest/tuning.html)

## 11. C++, Python launch, Lua 설정과 빌드

실습 파일의 역할을 구분한다.

| 파일 | 주된 역할 |
| --- | --- |
| C++ 소스 | Cartographer의 실제 알고리즘 구현 |
| Python launch | ROS 2 노드 실행 및 실행 옵션 구성 |
| Lua 설정 | Cartographer 알고리즘 파라미터 지정 |

**메모 정정:** Python launch에서 C++ 노드를 실행하는 것은 정상적인 구성이다. 두 언어를 함께 쓴다는 이유로 “CPU 충돌”이 발생하지 않는다. C++ 코드를 Python 문법처럼 붙여 넣으면 문법·실행 오류가 날 수 있고, 연산이 과하면 CPU 부하가 커질 수 있지만 서로 다른 문제다.

소스나 설치 대상 설정을 수정했다면 일반적으로 워크스페이스 최상위에서 다음 흐름으로 반영한다.

```bash
# 실제 ROS 2 워크스페이스 최상위 디렉터리에서 실행
colcon build
source install/setup.bash
```

`colcon build`는 패키지를 빌드·설치하고, `source`는 현재 셸에서 설치된 패키지를 사용할 환경을 설정한다. 새 터미널에도 필요한 환경을 적용해야 한다. [colcon 빠른 시작](https://colcon.readthedocs.io/en/released/user/quick-start.html)

- C++ 구현을 바꾸면 재빌드가 필요하다.
- Lua·launch 변경의 반영 방식은 설치 복사 여부와 심볼릭 링크 구성에 따라 다르다.
- 실행 중인 노드가 파일 변경을 자동 반영한다고 가정하지 않는다. 설정을 다시 읽도록 재실행한다.
- 수정했는데 변화가 없다면 launch가 실제로 읽는 설정 경로부터 확인한다.

- [ ] `max_angle_radians`의 철자와 단위를 확인했다.
- [ ] 격자 해상도와 Voxel 크기의 차이를 설명할 수 있다.
- [ ] 직진·회전·출발점 복귀 구간을 비교했다.
- [ ] 설정을 하나씩 바꾸고 원래 값과 결과를 기록했다.
- [ ] 지도 품질과 계산 지연을 함께 확인했다.
- [ ] 필요한 빌드·환경 적용·노드 재실행을 마쳤다.
