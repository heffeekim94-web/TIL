## 세 역할: 계획 · 제어 · 학습

- **planner(계획기)**: 경로를 만듦 / **controller(제어기)**: 상태를 보며 각 관절이 어떻게 움직일지 명령 발행 / **policy(정책)**: 관측을 보고 행동을 고름
- 계획 궤적 추종과 정책 추론은 다른 실행 모드 → 같은 관절에 여러 노드가 동시에 명령하지 않게 선택기를 둠 (제어권은 하나)
- 전체 흐름: 카메라·관절 → 인식·좌표변환(물체 자세/TF) → 계획 또는 정책 → 구동기
  - YOLO 의 2D 상자를 바로 팔의 3D 목표로 쓰지 않음. 자세 추정·깊이·TF·관절 피드백의 시간과 좌표를 맞춤

## 로봇 파일의 역할

| 파일 | 역할 |
|---|---|
| URDF | 기구 (링크·관절) |
| SRDF | 계획 그룹 (MoveIt) |
| XRDF | cuMotion 용 구성 (충돌 구 등) |
| USD | 시뮬레이션 물리·센서·장면 |

- 관절 이름과 TCP(도구 기준점)는 모든 파일에서 일치시켜야 함

## 순기구학(FK) · 역기구학(IK)

- FK: 관절값 → 도구 위치. `T_base,TCP(q) = T₁(q₁) · T₂(q₂) · … · T_n(q_n)`
  - 관절 하나씩 + 방향으로 움직여 URDF 축·원점이 맞는지 확인
- IK: 목표 TCP → 관절값. 해가 여러 개일 수도, 작업 공간 밖이면 없을 수도 있음
  - 관절 한계·충돌·현재 자세와의 거리를 함께 고려. 자유도가 부족한 팔에 임의의 6D 자세를 요구하지 않기

## MoveIt 2 설정

- MoveIt 2 는 URDF 를 가지고 알아서 관절 제어 입력을 만들어 줌
- **planning group(플래닝 그룹)**: 함께 계획할 관절 집합. 예) arm 그룹에는 팔 관절 체인만, TCP·집게는 팔의 일부가 아니라 별도 그룹(end effector)으로
- 손목 링크와 실제 물체를 잡는 기준점(TCP)은 다를 수 있음 → 목표 좌표가 어느 링크 기준인지 확인
- 조건: 충돌 방지, 정해진 IK 값대로 움직이는지. 선 꼬임 방지용 관절 각도 범위는 직접 입력
- **충돌 검사**: 팔·집게·잡은 물체까지 포함. 충돌쌍을 다 제외하면 경로는 쉽게 나오지만 실제로는 못 지나감
  - 자동 생성된 충돌 제외 목록(collision matrix)을 그대로 믿지 말고 실제 관절 범위에서 확인, 제외한 이유 기록
- 설치 순서: Setup Assistant 로 내 로봇 설정 → 가상 제어로 OMPL(샘플링 기반 계획) Plan·Execute 먼저 → 그다음 cuMotion 추가

## cuMotion · cuRobo

- **cuMotion**: GPU 로 로봇 모델·목표·장애물을 고려한 궤적을 계산. MoveIt 플러그인 + cuMotion 서버 + 내 URDF/XRDF 필요. 실제 모터 통신은 ros2_control 이나 드라이버 담당
- XRDF 충돌 구: 너무 작으면 충돌을 놓치고, 너무 크면 통로를 막음
- **cuRobo(V2)**: GPU 운동 생성 연구 도구, 비용·동역학을 직접 연구할 때. cuMotion(ROS 통합)과 다름
- 계획 계산 시간과 전체 시스템 지연은 다름. 장애물이 움직이면 replanning(다시 계획)
- (메모) 프로젝트 3 은 다중 로봇 제어 · 충돌 방지 → cuMotion

## ros2_control

- controller → hardware interface → 모터 ↔ 센서. 명령을 쓰고 관절 상태를 읽음
- command interface(position/velocity/effort)는 실제 구동기가 지원하는 방식으로, **driver 와 똑같이 정의되어 있는지 확인**
- 명령값을 실제 측정값처럼 되돌려 보내지 않기
- 축 방향이 반대로 되어 있으면 겉보기엔 비슷해도 실제 로봇이 망가질 수 있음 → 실제 로봇과 움직임이 같은지 꼭 확인
- 컨트롤러 이름·관절 목록·MoveIt Action 경로를 맞추고, 계획 성공과 실행 성공을 따로 확인
- **MoveIt Servo**: 마지막 위치 보정용 (목표 − 현재를 보며 반복 보정). 긴 장애물 우회는 계획기 담당
- 힘 제어: 임피던스(위치 오차 → 힘), 어드미턴스(측정된 힘 → 운동). 모터 전류만으로 외력을 정확히 안다고 가정하지 않기
- 집기 작업은 단계별 상태 머신(MTC): 접근 → 집기 → 들기·운반 → 놓기·확인, 실패하면 재탐색·재접근·종료 중 어디로 갈지 정함
- nvblox: 깊이 영상으로 ESDF(장애물까지 거리장)를 만들어 계획기에 장애물로 넘김. 로봇 자신·잡은 물체 처리도 정해야 함

## 정책학습 (강화학습)

- 정책 `a_t ~ πθ(a | o_t)`: 관측 o → 행동 a. 학습은 가중치를 바꾸고, 추론은 고정 가중치로 실행
- 강화학습 반복: 관측·정책 → 행동·환경 → 보상·다음 관측. 목표는 한 순간이 아니라 에피소드 전체의 누적 성과
- **PPO 는 알고리즘, RSL-RL 은 학습 실행 라이브러리** (RCL-RL 아님)
  - PPO: 확률비 `r_t = πθ / πold` 를 `[1−ε, 1+ε]` 로 잘라(clip) 정책이 한 번에 크게 바뀌지 않게 함
  - Actor 는 행동을 고르고 Critic 은 앞으로의 가치를 추정. 시뮬 정답은 Critic 에만 줄 수 있지만 Actor 입력은 실제 로봇에서 얻을 수 있어야 함
- 환경 설계
  - 관측: 관절 위치·속도, TCP 오차, 집게 상태, 이전 행동 등. 이름·순서·단위·좌표계 문서화
  - 행동: `q_target = clip(q_reference + scale × a, q_min, q_max)`, q_reference 가 현재 관절인지 고정 기준인지 명시
  - 보상: `r = −w_d·d − w_a·||Δa||² − w_c·c + w_s·s` (거리·급격한 행동·충돌 비용, 성공 보상). 거리만 줄이고 물체를 놓치는 편법을 막으려 성공 판정은 따로
  - 리셋(다음 시도 초기조건)과 종료(terminated: 성공·실패 / truncated: 시간 제한)를 따로 설계
- 학습 순서: 무행동 → 작은 임의 행동 → 짧은 PPO 학습 → checkpoint 재생 → 병렬 환경 확대. 처음부터 수천 개 환경을 켜서 원인을 숨기지 않기
- 명령: `bash scripts/lab.sh train --task Practice-Reach-OwnArm` (physics=isaacsim_physx), 평가는 play
- 평가: 학습 보상만 보지 말고, 학습에 안 쓴 초기조건에서 성공률·위치 오차·충돌·완료 시간·추론 지연 기록
- sim-to-real: 질량·마찰·지연·센서 잡음 차이 → 실제 측정 범위를 도메인 랜덤화로 반영

## 모방학습 · VLA

- 모방학습: 사람 시연의 (관측, 행동)을 정답 쌍으로 학습. 카메라 프레임과 명령 시각을 맞추고, 에피소드·촬영 세션 단위로 train/val/test 분리 (YOLO 때 영상 단위로 나눈 것과 같은 이유)
- Mimic: 시연을 물체 배치를 바꿔 새 데이터로 확장, 실패한 변환 궤적은 제외
- BC(시연 행동 맞추기) · ACT(행동 묶음 예측) · Diffusion Policy(잡음에서 행동 시퀀스 복원)는 서로 다른 알고리즘
  - Diffusion: 여러 단계 추론이라 지연과 행동 실행 길이를 함께 측정
- GR00T(VLA = Vision-Language-Action): 영상·언어·상태 → 행동. 내 로봇은 modality key·단위·상대/절대 행동·집게 범위·주기를 맞춰 미세조정. 별도 venv 에 고정 버전으로 설치

## 배포 · 디버깅

- 배포: 관측 어댑터 → 정책·제한·선택 → 구동기 드라이버. 상태가 오래되거나 NaN 이면 유지·정지(watchdog)
- 비교표: MoveIt/cuMotion vs PPO vs 모방학습을 같은 초기조건에서 성공률·충돌 수·시간·지연으로 비교
- 디버깅 순서: 모델 형상 → 한 관절 → 상태 수신 → 작은 명령 → 계획 → 학습. 학습 전에 실패한 것을 더 긴 학습으로 해결하려 하지 않기
- 완료 기준: 다른 사람이 재현 가능하게 (URDF/USD/SRDF/XRDF, 코드, 버전 기록, checkpoint, 평가표, 영상). 실기 미검증 항목은 그대로 표시

## 오늘 YOLO · 경량화 작업에서 배운 것

- **best epoch 를 작은 val 로 고르면 운이 섞임**: 1단계(합성)를 val 68장으로 고르니 epoch 9 가 뽑혔고, 거기서 출발한 최종 모델은 0.907. 같은 학습을 33 epoch 으로 고정하니 0.949 → 학습 단계를 끊는 기준은 val 이 작을수록 고정값이 더 안정적
- **재현 가능한 숫자를 최종으로**: 점수가 조금 높아도(0.969) 레포에 없는 데이터로 고른 모델이면 팀원이 같은 결과를 못 냄 → README 의 방법 그대로 나오는 모델을 최종으로
- **경량화 비교는 같은 조건으로**: imgsz · batch · conf · IoU 를 고정하고, 지연은 전처리 + 추론 + NMS 를 다 넣어 평균과 p99 를 같이 봄
- **FP16 은 정확도 손실이 거의 없음**: 클래스별 AP 차이 최대 0.001, 크기 절반, GPU 에서 가장 빠름
- **INT8 이 mAP 0 이 되는 이유**: YOLO 출력 하나에 상자 좌표(0~960)와 점수(0~1)가 같이 들어 있어, int8 눈금 하나(약 3.8 단위)로 줄이면 점수가 0 이 됨 → 마지막 검출 층은 FP32 로 둠
- **INT8 은 장치를 가림**: ORT CUDA EP 에는 빠른 int8 커널이 거의 없고, CPU 에서도 FP32 보다 빠르지 않았음. INT8 이 빨라지는 곳은 TensorRT

## 오늘 ROS 노드에서 배운 것

- **resource/<패키지명>**: Python 패키지(ament_python)가 ROS 에 "설치됨"을 알리는 빈 표시 파일. C++ 패키지(ament_cmake)는 `ament_package()` 가 자동으로 만들어서 필요 없음
- **launch 파일은 C++ 로 못 씀**: ROS 2 launch 는 Python · XML · YAML 만 지원. config YAML 은 코드가 아니라 노드가 읽는 설정값
- **ONNX Runtime C++**: provider(cuda · tensorrt · cpu)를 골라 같은 .onnx 를 PC · Jetson 에서 실행. 입력 크기와 클래스 이름은 모델 메타데이터에서 읽음
- **C++ 에서 ROS 파라미터 타입은 엄격함**: YAML 의 `70` 은 int, `70.0` 은 double → 선언한 타입과 다르면 노드가 시작하지 못함
