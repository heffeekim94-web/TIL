## 문제 4 - 제어와 통신의 역할 해석


### Tasks

| 항목 | 설명용 조건·기록 |
|----|----|
|제어 계산 |	    OpenCR에서 10ms마다 수행|
|상태 발행 |            	 100ms마다 수행|
|0.0초    |	PC가 /motor/target에 30.0 발행|
|0.1초    |	PC가 /motor/state에서 2.0 수신|
|0.5초    |	PC가 /motor/state에서 12.0 수신|
|1.0초    |	PC가 /motor/state에서 22.0 수신|
|2.0초    |	PC가 /motor/state에서 29.0 수신|

1. PC ROS 2 노드–micro-ROS Agent–OpenCR–다이나믹셀의 연결 구조도에 목표 전달과 측정값 반환 방향 표시
2. 송신자·수신자와 주기 비교
3. 통신 단절 시 오래된 명령 처리 정책 및 이유

`제출 증거`: 
- 구조도와 짧은 답변. 
- 실제 통신 단절 시험이나 새 연동 환경 구축은 요구하지 않습니다. 
- 이 문항은 구조와 기록 해석을 평가하며 micro-ROS 구현 성취를 인증하지 않습니다.

---

### 1. 시스템 구성도

```
┌──────────────────────┐
│    PC ROS 2 노드     │
│ 목표 발행 / 상태 수신 │
└─────────────────────┘
     │            ▲
     │ 목표각      │ 현재각
     │ /motor/    │ /motor/
     │ target     │ state
     ▼            │
┌──────────────────────┐
│   micro-ROS Agent    │
│    양방향 통신 중계   │
└──────────────────────┘
     │            ▲
     │ 목표 전달   │ 상태 전달
     ▼            │
┌──────────────────────┐
│       OpenCR         │
│ 제어 계산: 10 ms마다  │
│ 상태 발행: 100 ms마다 │
└──────────────────────┘
     │            ▲
     │ 제어 명령   │ 위치 측정값
     ▼            │
┌──────────────────────┐
│      다이나믹셀       │
│ 모터 구동 / 위치 측정  │
└──────────────────────┘
```

- 목표 전달 방향  
  `PC ROS 2 노드 → micro-ROS Agent → OpenCR → 다이나믹셀`
- 상태 반환 방향  
  `다이나믹셀 → OpenCR → micro-ROS Agent → PC ROS 2 노드`


micro-ROS Agent는 제어 계산을 하는 장치가 아니라, PC 측 ROS 2 통신과 OpenCR 측 micro-ROS 통신을 중계하는 역할입니다.

### 2. 송신자와 수신자 표


| 데이터/토픽 | 송신자 | 수신자 | 방향 | 의미·단위 |
|---|---|---|---|---|



- `/motor/target`: PC가 발행하고 OpenCR이 수신
- `/motor/state`: OpenCR이 발행하고 PC가 수신
- 다이나믹셀: OpenCR로부터 모터 명령을 받고 실제 속도 상태를 반환
- micro-ROS Agent: 양방향 메시지 중계

- 이번 문제의 기존 8강 인터페이스: 회전 속도, 단위 `RPM`
- 문제 1에서 사용한 인터페이스: 목표·현재 위치는 `°`, 제어 출력은 `°/s`

즉, 이번 문제의 `30.0`, `2.0`, `12.0` 등을 각도값으로 해석하면 안 됩니다.

## 4. 주기 비교와 계산 횟수

`### 3. 제어 주기와 상태 발행 주기 비교`로 작성하면 됩니다.

먼저 작은 표로 정리하세요.

| 항목 | 주기 | 주파수 |
|---|---:|---:|
| 제어 계산 | 10 ms | 100 Hz |
| 상태 발행 | 100 ms | 10 Hz |

그다음 계산식을 직접 적으세요.

```text
상태 발행 한 주기 동안의 제어 계산 횟수
= 상태 발행 주기 / 제어 계산 주기
= 100 ms / 10 ms
= ?
```

결과만 쓰지 말고 계산식을 보여줘야 주기 비교 평가를 확실히 받을 수 있습니다. 여기서 “상태를 한 번 보낼 때까지 OpenCR 내부에서는 제어 계산이 몇 차례 수행되는가”를 해석하면 됩니다.

## 5. 가상 기록 해석

`### 4. 목표 속도와 현재 속도의 변화` 아래에 주어진 기록을 다시 표로 정리하세요.

추천 열은 다음과 같습니다.

| 시간 [s] | 목표 속도 [RPM] | 현재 속도 [RPM] | 속도 오차 [RPM] | 목표 대비 비율 [%] |
|---:|---:|---:|---:|---:|

계산 기준:

```text
속도 오차 = 목표 속도 - 현재 속도
목표 대비 비율 = 현재 속도 / 목표 속도 × 100
```

해석할 때 확인할 포인트는 다음입니다.

- 현재 속도가 시간에 따라 목표 속도에 접근하는지
- 오차의 크기가 감소하는지
- 목표 속도를 초과하는 오버슈트가 기록에 나타나는지
- 2초 상태가 목표와 정확히 같은지, 약간의 오차가 남았는지

0초에는 `/motor/target` 발행만 주어졌으므로, 주어지지 않은 현재 속도를 임의로 `0 RPM`이라고 기록하지 않는 편이 정확합니다.

또한 과제에서 이 값은 가상 기록이라고 명시했으므로, “실험으로 확인했다”가 아니라 “주어진 기록에서는 이렇게 해석된다”는 식으로 구분하세요.

## 6. 통신 단절 정책

`### 5. 통신 단절 시 오래된 명령 처리 정책`에는 다음 네 부분이 들어가면 좋습니다.

1. 단절 감지 방법
2. 오래된 명령에 대한 처리
3. 재연결 후 동작
4. 정책을 선택한 이유

안전한 정책 방향은 다음과 같습니다.

- PC가 목표 명령 또는 heartbeat를 일정 주기로 갱신
- OpenCR이 마지막 수신 시각을 저장
- 정한 제한 시간 동안 새 명령이 없으면 명령을 오래된 값으로 판정
- 이전 `30 RPM`을 계속 유지하지 않고 정지 방향으로 전환
- 갑작스러운 정지가 위험하다면 속도를 단계적으로 `0 RPM`까지 감소
- 재연결되더라도 이전 명령을 자동 재사용하지 않고 새 유효 명령을 받은 뒤 다시 구동
- PC에도 timeout/fault 상태를 알림

중요한 해석 포인트가 하나 있습니다. 예시처럼 목표를 0초에 단 한 번만 보내는 구조라면, OpenCR은 PC가 끊겼는지 단순히 판단하기 어렵습니다. 따라서 단절 정책을 쓰려면 “PC가 명령을 주기적으로 재전송한다” 또는 “별도 heartbeat를 사용한다”는 조건도 함께 제안해야 논리가 완성됩니다.

## 최종 점검

평가 기준에 맞춰 다음이 모두 보이면 됩니다.

- 구조도에 네 구성요소와 양방향 흐름이 있음
- `/motor/target`, `/motor/state`의 송신자와 수신자가 명확함
- `10 ms`와 `100 ms`를 직접 계산하여 비교함
- `RPM`과 기존 보고서의 `°`, `°/s`를 혼동하지 않음
- 단절 감지 조건, 정지 방법, 복구 조건, 안전상의 이유가 있음
- 가상 기록을 실제 실행 결과처럼 표현하지 않음

기존 보고서처럼 표 뒤에 짧은 `해석:` 문단을 붙이는 형식이 가장 잘 어울립니다.
